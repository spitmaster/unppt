# 多仓工作区指南（Workspace 模式）

> 当一个产品横跨多个代码仓库（如前端 2 个仓 + 后端 3 个仓）时，用本指南把 SDD 脚手架升级为 **Workspace 模式**：一个中心仓持有产品级真相源，各代码仓只放薄入口。
> 单代码库项目不需要读本文，按 `01-使用说明.md` 走单仓模式即可。

---

## 解决什么问题

单仓模式在多仓产品下会坏在四处：

1. **SPEC 无单源**：一个功能同时改多个仓，跨仓需求和端到端验收标准没有归属地
2. **契约无家可归**：前后端之间的 API/事件契约没有位置放，各仓口口相传
3. **脚手架 ×N**：`docs/` 与 agent 库要 init N 次、update N 次，必然漂移
4. **AI 视野受限**：会话在一个仓里工作时看不到调用方/被调方代码

Workspace 模式的答案：**真相源上移一层，代码仓下沉为成员**。

---

## 目录布局

```
my-product/                        ← workspace 根（AI 会话从这里启动）
├── CLAUDE.md                      ← 产品级入口（模板：docs/ai-config/for-claude-workspace.md）
├── SPEC.md                        ← 产品级 SPEC：跨仓需求 + 端到端验收
├── docs/                          ← 全套 SDD 文档，只此一份
│   ├── contracts/                 ← 跨仓契约：API / 事件 / 共享模型
│   └── repos/                     ← 各仓代码现状摘要（/sdd-starter:digest 生成的派生快照）
├── .claude/agents/                ← agent 库只装一份
├── repos.md                       ← 仓注册表（有 .gitmodules 时可省略）
├── frontend-a/                    ← 成员仓（submodule 或普通 clone）
│   ├── CLAUDE.md                  ← 薄入口（模板：docs/ai-config/for-claude-member.md）
│   └── SPEC.md                    ← 仓级 SPEC：只写本仓实现切面
├── frontend-b/
├── backend-a/  backend-b/  backend-c/
```

**分层规则（MUST）**：

| 内容 | 住哪 | 不允许 |
|------|------|--------|
| 跨仓需求、端到端验收标准 | workspace `SPEC.md` | 复制进任何仓级 SPEC |
| 仓间 API/事件/共享模型契约 | workspace `docs/contracts/` | 只改某个仓的调用代码不回写契约 |
| 各仓代码现状摘要（派生快照） | workspace `docs/repos/` | 当真相源引用——真相是子仓代码 |
| 本仓的实现切面（改哪些模块、仓内验收） | 成员仓 `SPEC.md`（仅受控仓） | 写别的仓该做什么 |
| 文档体系、agent 库 | workspace 一份 | 在成员仓重复安装（除非脱离 workspace 单仓使用） |

## 成员仓的两级接入（受控仓 / 外部仓）

成员仓可能由**其他团队开发**，不能假定他们接受 SDD 约定。按接入意愿分两级，init 时逐仓确认：

| | 受控仓 | 外部仓 |
|--|--------|--------|
| 谁开发 | 本团队 | 其他团队/外部协作方 |
| 落薄入口（CLAUDE.md + 仓级 SPEC） | ✅ | ❌ 不落任何文件（对方仓零侵入） |
| 契约纪律 | 契约先行（MUST） | 靠 `/sdd-starter:digest` 漂移检测事后发现 |
| 主仓如何了解它 | 薄入口 + 仓级 SPEC + digest 摘要 | **仅 digest 摘要**（`docs/repos/<仓>.md`） |

这种形态下 workspace 主仓退化为**纯文档仓**：产品级 SPEC + 契约 + 各仓派生摘要，自身不含业务代码——完全成立，且是外部协作场景的推荐形态。

## 仓注册表

插件命令按以下优先级解析成员仓清单：

1. **`.gitmodules`**（submodule 布局）——git 原生、机器可读、一键克隆
2. **`repos.md`**（普通 clone 布局）——手工登记表，格式见 `docs/templates/repos模板.md`

两种布局对插件等价，选择只取决于团队 git 工作流（见下节）。

---

## Submodule 布局的三个驯化补丁

选 submodule 时**必须**配齐三补丁，否则会掉进经典陷阱（指针噪音 / detached HEAD / 推送顺序依赖）：

1. **`ignore = all` + `branch = <主分支>`**：每个 submodule 在 `.gitmodules` 里配置，`git status` 不再刷指针噪音，日常把子仓当普通 clone 用

   ```ini
   [submodule "backend-a"]
       path = backend-a
       url = git@example.com:team/backend-a.git
       branch = main
       ignore = all
   ```

2. **指针只在门禁时刻 bump**：日常不追"最新"，只在版本验收/发布时提交一次快照（workspace 的一个 commit 钉死 N 个仓的 commit = 可回溯的验收基线）。平时指针过时是**设计内状态**
3. **禁用 `git submodule update` 于脏工作区**：成员仓代码以其工作区分支为准；只有做快照校验时才 update。团队约定写进 workspace CLAUDE.md

不需要"跨仓一致性快照"能力的团队，用普通 clone + `repos.md` 更省心（workspace 仓把成员仓目录加进 `.gitignore`）。

## 跨仓功能的工作流

```
需求
 → ① 产品级 SPEC 立项：跨仓需求 + 端到端验收标准（workspace/SPEC.md）
 → ② 拆解矩阵：涉及仓 × 各仓交付物（写在产品级 SPEC 的功能条目下）
 → ③ 契约先行：仓间新增/变更的接口先落 docs/contracts/，各仓引用不复制
 → ④ 仓级展开：各成员仓 SPEC.md 写本仓实现切面，引用产品级条目号
 → ⑤ 各仓开发：可由 project-orchestrator / miniprogram-orchestrator 等 agent 按仓分派
 → ⑥ 跨仓联调验收：对照产品级验收标准 + 契约逐条核对；（submodule 布局）通过后 bump 指针做快照
```

**契约变更纪律（MUST）**：任何仓间接口变更，先改 `docs/contracts/` 再改代码；只改调用方/提供方代码不回写契约 = 破坏真相源。

## 成员仓的降级模式

成员仓被**单独打开**（单仓 clone、CI 流水线、只负责一个仓的同事）时，薄入口 CLAUDE.md 的降级规则生效：

1. 探测 `../CLAUDE.md`（workspace 入口）是否存在
2. 存在 → workspace 模式：产品级问题读 `../SPEC.md`，契约读 `../docs/contracts/`
3. 不存在 → **单仓降级**：以本仓 `SPEC.md` 为准工作；涉及仓间契约的判断标注「未与 workspace 校验」，不臆断对端行为
4. 长期脱离 workspace 使用 → 在本仓跑 `/sdd-starter:init` 升级为完整单仓脚手架（逃生口，不是默认）

## 命令行为差异（workspace vs 单仓）

| 命令 | 单仓模式 | workspace 模式 |
|------|---------|---------------|
| `/sdd-starter:init` | 现行为 | init 时主动询问仓数量，多仓即引导进本形态：布局引导（submodule / 普通 clone）→ 建 workspace 骨架 → 注册表 → 逐仓确认接入级别、受控仓落薄入口 |
| `/sdd-starter:update` | 现行为 | 刷新中心 docs/ + agents + 受控仓刷新薄入口（.template 方式） |
| `/sdd-starter:check` | 现行为 | 额外按注册表逐仓核对：可达性、接入级别、薄入口、摘要新鲜度 |
| `/sdd-starter:digest` | 不适用 | **子仓 → 主仓文档摘要**：只读各仓代码现状，总结写入 `docs/repos/`，检测契约漂移（用户主动触发） |

形态确定方式：`init` **主动询问**用户仓数量（目录特征仅用于给推荐项）；update / check / digest 按已落地的注册表与入口标记自动识别。
